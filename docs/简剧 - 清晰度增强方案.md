# 简剧 · 视频清晰度增强方案

> 状态：**A 已实现；B 已实现后因实测黑屏整体移除；C 待实现**
> 关联代码：`lib/core/services/line_quality.dart`、`play_lines.dart`、`prebuffer_service.dart`、`player_page.dart`
> 设置入口：设置 → 播放器 →「清晰度优先选线路」（播放页顶栏「画质」按钮为快捷入口）

---

## 一、背景与目标

用户需求：希望能配置 **1080p / 2K / 4K**，把视频清晰度提高到所设置的档位。

本文档先给出**实测结论**（哪些路走得通、哪些走不通），再拆成三条可落地的路径：

| 路径 | 名称 | 是否实现 | 能否拿到「真细节」 |
| --- | --- | --- | --- |
| **A** | 清晰度优先选线路 | ✅ 已实现 | ✅ 能（码率差 2 倍 = 真实画质差 2 倍） |
| **B** | 高画质渲染（mpv 放大/锐化调优） | ❌ **已移除**（真机黑屏，见第四节） | ⚠️ 感知提升，不产生新细节 |
| **C** | AI 超分（Anime4K / FSR → 1080p/2K/4K） | ⏳ 待实现 | ✅ 能产生接近真实的细节 |

---

## 二、实测结论（2026-10，16 个真实源样本）

在写代码前对源站做了实地探测，结论直接决定了方案形态：

### 2.1 源站没有多档清晰度可选

| 发现 | 实测数据 |
| --- | --- |
| 所有 master 清单**只有 1 个 variant** | 16 个样本，`EXT-X-STREAM-INF` 计数最大值 = **1** |
| 声明分辨率只有两档 | `720x1280`（竖屏短剧）/ `1080x608`（横屏） |
| 实测码率 | **469 ~ 1002 kbps**，不到 1Mbps |
| `$$$` 分组不是清晰度档 | 同一集的 6 个源组（`play.hhuus.com`、`1080p.huyall.com`、`hd.ijycnd.com`、`hn.bfvvs.com`…）首片字节数**完全相同 = 611200B**，是同一份文件的 CDN 镜像 |

> 叫 `1080p.`、`hd.` 的域名是**营销命名，不是真档位**。`vod_play_from` 里的 `sdm3u8 / wjm3u8 / ...` 分组是线路（CDN 镜像），不是清晰度档。

**推论：「从源里选 1080p/2K/4K」这条路不存在——没有可选的东西。**

### 2.2 但不同站点之间码率差异巨大

实测不同站点的码率分布：`469 / 672 / 1002 / 1138 kbps`——**差 2.4 倍**。

而 `PlayLineResolver` 原本是按**「最快」**竞速排序（`play_lines.dart` `scoreOf` = EMA 耗时 + 失败惩罚），**完全没有考虑清晰度**。

**这是唯一能拿到「真细节」的抓手，即路径 A。**

### 2.3 播放器侧零画质调优

`player_page.dart` 的 `_applyMpvTweaks()` 原本只设了 5 条音视频/网络属性，**没有任何画质属性**，全部走 media_kit 的省电级默认值（见 `media_kit-1.2.6/.../real.dart:2397-2406`）：

```
scale=bilinear   dscale=bilinear   dither=no
correct-downscaling=no   sigmoid-upscaling=no
```

`bilinear` 是**质量最低**的放大算法，720p 放大到屏幕分辨率时明显发糊。这是路径 B 原本的抓手——**但真机上走不通**，见第四节。

## 三、路径 A：清晰度优先选线路 ✅

### 3.1 思路

在**不增加起播延迟**的前提下，让线路竞速优先挑码率更高的线路：

1. 线路解析成功后，**后台**探测该直链的首片码率（`Range: bytes=0-0` 取分片总字节 ÷ `EXTINF` 时长）；
2. 码率按线路 id 持久化到 `local.play_line_stats`（新增 `br` 字段，单位 kbps）；
3. 开关打开时，播放用的线路排序从「耗时优先」改为「**码率降序 → 耗时升序**」；
4. 探测失败记 `br = 0`（视为已探测但失败），**不反复重试**，避免打爆站点。

### 3.2 关键设计取舍

| 决策 | 理由 |
| --- | --- |
| 探测在**后台** fire-and-forget，不 await | 起播零延迟，首播即返回第一个成功的线路 |
| 只探测 `br` 缺失的线路 | 结果持久化后每条线路基本只探一次（约 2 个请求） |
| 未知码率按**占位值 800 kbps** 参与排序 | 首播全部未知 → 全部 800 → 并列后按耗时分先后，**与旧行为完全一致**；比记 `-1` 更稳（`-1` 会让未知永远垫底，反而把没测过的慢线压到最后） |
| 连续失败 ≥2 的线路强制降到占位值 | 它已经证明不稳，即便历史码率高也不该继续抢在前面 |
| 新增 `orderedLinesForPlay()`，不改 `orderedLines()` | `orderedLines()` 还被跨站搜索用作**结果优先级**（`api_service.dart:267`），不该被码率排序污染 |
| 开关关闭时完全不探测、不改变排序 | 关 = 行为与旧版逐字节一致 |

### 3.3 多档 master 的变体选择（前瞻）

虽然当前 16 个样本都是单档，但 `_firstVariant()` 原本**只取清单第一个变体、不读 `BANDWIDTH`/`RESOLUTION`**。

路径 A 打开时，起播改写与跨集预缓存两条路径改为解析 `#EXT-X-STREAM-INF` 的 `BANDWIDTH`，**选带宽最高的变体**；并且在「源是多档 master」时，即便没有广告也走改写清单，把选中的高档位锁定下来（否则交回 mpv 自选，可能取到低档）。

> 关闭时保持旧逻辑（取第一个变体），行为不变。

### 3.4 涉及代码

| 文件 | 改动 |
| --- | --- |
| `lib/core/services/line_quality.dart` | **新增**：变体解析（纯函数）+ 码率探测 |
| `lib/core/services/play_lines.dart` | `PlayLineStat` 增加 `bitrateKbps`；`orderedLinesForPlay()`；`_recordBitrate()`；`_resolveOnLine` 成功后后台探测 |
| `lib/core/services/prebuffer_service.dart` | `_firstVariant` → 支持按 BANDWIDTH 选最高档；`removed==0` 时多档 master 仍走改写 |
| `lib/core/constants/app_constants.dart` | `keyLineQualityFirst` + 默认值 |
| `lib/core/services/settings_service.dart` | `lineQualityFirst` 读写 |
| `lib/core/state/settings_provider.dart` | 字段 + setter |
| `lib/pages/settings/settings_page.dart` | 开关 UI |

### 3.5 成本与限制

- **成本**：每条线路约 2 个后台请求（1 个清单 + 1 个 1 字节 Range），全部成功后不再探测。
- **限制 1**：只在「已成功解析的线路」之间比较，不会为了找更高码率而延长竞速。
- **限制 2**：码率按**线路**统计，同一站点不同剧的码率会有波动（CDN 编码档位通常按站一致，误差可接受）。
- **限制 3**：源站本身只有 ~720p，A 只能帮你**选到最好的那份 720p**，不能凭空变出 1080p。

## 四、路径 B：高画质渲染 ❌ 已移除（2026-10）

### 4.1 原方案

通过 mpv 的 `setProperty`（复用 `_applyMpvTweaks()` 现有通道）替换掉 media_kit 的省电级默认值，用**更高质量的放大/缩小算法**把 720p 源投到屏幕分辨率时的观感拉起来：

| mpv 属性 | media_kit 默认 | 曾经的「打开」值 | 作用 |
| --- | --- | --- | --- |
| `scale` / `cscale` | `bilinear` | `ewa_lanczossharp`（完整档）/ `lanczos`（轻量档） | 视频/色度平面放大算法 |
| `dscale` | `bilinear` | `mitchell` | 缩小算法 |
| `correct-downscaling` | `no` | `yes` | 先降采样再缩放，细线不糊 |
| `sigmoid-upscaling` | `no` | `yes` | 高对比边缘防振铃 |
| `dither-depth` | — | `auto` | 输出位深抖动，渐变不带状 |
| `sharpen` | — | `0.05` | 轻微锐化 |

曾做过两档（1 轻量 = 只换 `scale/cscale/dscale`；2 完整 = 再加 FBO 后处理与锐化），以备降档绕过驱动问题。

### 4.2 真机实测结果：**两档都黑屏**

测试机：**华为 P30 Pro（VOG-AL10）/ Kirin 980 / Mali-G76 / Android 10**。

| 现象 | 证据 |
| --- | --- |
| 开启后**有声无画**（纯黑屏，音频正常） | 用户反复实测：完整档、轻量档（`scale=lanczos` + `cscale=lanczos` + `dscale=mitchell`）均黑屏 |
| 关闭后恢复正常 | 关闭走回 `scale=cscale=dscale=bilinear` 即出画面 |
| 根因是 GPU 缩放/后处理路径 | logcat 中大量 `WaitGpuAcquireFence: Sync wait 15275 over 6000 !`（开启时段 224 次/分钟），关闭后骤降 |
| 属已知驱动缺陷，非本项目 bug | mpv-android **#292**（任何非默认缩放/锐化黑屏）、**#392**（"no video if any scaling besides default is used"，报告机型正是 Huawei P30 Pro + Android 10） |

> 结论：在 Mali 系 GPU 上，**只要改掉 `bilinear` 就没有画面**，路径 B 无法通过任何属性组合绕过（`gpu-dumb-mode=yes` 能出画面但会把 HQ 缩放一并禁掉，等于功能不存在）。

### 4.3 处理方式（已执行）

按用户要求「解决不了就移除」，整段功能已从代码中删除，不留死开关：

- `player_page.dart`：`_applyMpvTweaks()` 恢复为只写音频/缓冲/UA 属性，并加注释说明**不要碰 scale/cscale/dscale**；删除 `_watchSettings()` / `_onSettingsChanged()` 实时重下监听。
- `settings_page.dart`、播放页「画质」弹层：删除「高画质渲染」开关与档位选择；弹层保留**当前线路码率/测速**与「清晰度优先选线路」。
- `app_constants.dart` / `settings_service.dart` / `settings_provider.dart`：删除 `keyRenderQuality`、`keyRenderQualityLevel`、`renderQuality*` 读写与默认值。
- 旧设备里遗留的 `settings.render_quality` 存储值不影响运行（已无读取方）。

**保留的唯一有效抓手是路径 A**（选更高码率的线路，真细节）。

### 4.4 若要重新引入（前置条件）

1. 在**非 Mali** 机型（Adreno/Mali 新代次）上验证 `scale=lanczos` 是否正常出画面；
2. 或改用**软件滤镜**路线（`vf=` lavfi/zimg，缩放在 CPU 侧完成，GPU 只做 bilinear blit）绕开驱动缺陷——需先确认 media_kit 打包的 libmpv 含 `libavfilter`，且 720p 实时开销可接受；
3. 路径 C 的 `glsl-shaders` 同样走 GPU shader，**大概率会撞上同一个驱动缺陷**，必须先在同一台 P30 Pro 上做冒烟测试再投入。

## 五、路径 C：AI 超分（待实现）

### 5.1 目标

真正把 720p **提升到 1080p / 2K / 4K**——只有超分辨率算法能产生接近真实的细节。

### 5.2 候选方案

| 方案 | 平台 | 实时性 | 模型体积 | 说明 |
| --- | --- | --- | --- | --- |
| **Anime4K** | Win + Android | ✅ 实时 | ~0（纯 shader） | 重绘边缘，短剧（人物/线条）效果最好，首选 |
| **FSR 1.0** | Win + Android | ✅ 实时 | ~0（纯 shader） | AMD 开源，通用放大，锐度适中，保底方案 |
| nnedi3 / waifu2x-ncnn | 仅 Win | ⚠️ 勉强 | 100~300MB | 真 AI，需 Vulkan 运行时，移动端不现实 |

### 5.3 接入方式

media_kit 的 `NativePlayer.setProperty('glsl-shaders', '<shader路径>')` 注入 mpv GLSL shader；shader 文件放 `assets/shaders/`，随包分发。

### 5.4 档位设计（对应用户的 1080p/2K/4K 需求）

```
AI 超分档位    关 / 1080p / 2K / 4K
```

**关键语义**：mpv 会自动把画面放大到**窗口分辨率**，所以档位的真实含义是
> 「用对应强度的超分算法放大到该分辨率」

而不是「从源里选该分辨率」（源里没有，见第二节）。

### 5.5 天花板（必须先说清楚）

| 场景 | 结果 |
| --- | --- |
| 屏幕 1080p，档位设 2K/4K | **毫无意义**——没有更多像素可填，建议按屏幕分辨率选档 |
| 720p → 1080p（1.5x） | ✅ Anime4K 效果不错 |
| 720p → 4K（5x） | ⚠️ 任何算法都只会「更锐」不会「有真细节」，建议只在 Windows 高分屏开放 |

### 5.6 实现前必须验证

1. media_kit 打包的 libmpv 是否支持 `glsl-shaders`（Windows 标准构建大概率支持，Android `vo=gpu` 需实测）；
2. Android 中端机跑 Anime4K 的帧率（掉帧就得降档）；
3. `rewritePlaylist` 改写为本地 `.m3u8` 后 shader 是否仍生效（理论在渲染层，应无影响，但要验证）。

